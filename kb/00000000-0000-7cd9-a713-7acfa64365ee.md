# CiaPoD

**Code is a product of documentation.**

I use a knowledge base to describe the desired state of my software: what it should do, the constraints it must respect, and why those choices matter. The code is an implementation of that description. When I change the implementation, I should be able to explain which documented intention it serves.

## Write down the desired state

A useful document says something concrete enough to guide a decision. It describes an outcome, names the relevant constraints, and makes success recognizable. It preserves the reasoning that another person, an agent, or my future self would otherwise have to reconstruct.

“Make backups reliable” leaves almost everything to interpretation. “Every irreplaceable file has a second copy that has been restored successfully, and a failed backup becomes visible” gives implementation and verification a direction. Tools can change while that intention remains useful.

The knowledge base connects these statements. Foundational documents describe standing philosophies. Other documents describe particular capabilities, decisions, work and checks. Links make their relationships explicit; scopes identify where an intention applies. [KINGSMetaL](00000000-0000-7348-ad47-04d09865aab0.md) supplies a consistent format and stable identities for those documents.

## Build from that description

The working loop is small:

1. Describe the desired behavior and the reason for it in the knowledge base.
2. Find the related intentions and constraints before choosing an implementation.
3. Change the code to realize that description.
4. Verify the result against the documented outcome, using executable checks wherever they can express it meaningfully.
5. Record what was learned and revise the documents when the intended state changes.

This loop applies whether a person or a coding agent writes the implementation. An agent needs enough context to make the right decisions; a linked knowledge base lets that context survive beyond a conversation or a single work session.

## Keep intention and observation distinct

A document describing a desired state does not prove the code already achieves it. Work records and verification results must make the gap visible. A passing check provides evidence for the behavior it checks; it does not prove every sentence in the knowledge base.

If implementation reveals an ambiguity or a bad assumption, resolve it in the documents as well as the code. If the desired behavior changes, update its description deliberately. Quietly rewriting the intention to excuse a defect loses the reason for having a specification.

## Preserve the reason

The knowledge base should let me answer: Why does this behavior exist? What would a replacement still have to satisfy? Which assumptions should be revisited when circumstances change?

Documentation has continuing value when it can answer those questions after the original author has forgotten the details. The implementation can then be repaired, replaced or regenerated with a clear account of what it is meant to accomplish.
